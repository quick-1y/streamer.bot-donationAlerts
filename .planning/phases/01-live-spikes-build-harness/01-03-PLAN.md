## Phase Goal

ROADMAP Phase 1 goal (verbatim): "Design decisions rest on behavior verified in the user's Streamer.bot 1.0.7. The source can be compile-checked offline and packaged from the repo into an importable `.sb`."

This is not in user-story form and is not rewritten here. This plan delivers success criterion 2a: "A golden `.sb` exported from the user's Streamer.bot 1.0.7, with no secrets, is stored in the repo". It also yields the first live observations for findings F1, F5 and E8.

<objective>
Get the real 1.0.7 export format from the user, vet it, and store it in the repo. The Russian recipe and a compile-checked golden runtime go to the user, who exports a small golden that contains only the recipe items. Claude audits and decodes it, and the user approves it at a blocking-human checkpoint before it is committed.

Purpose: the builder (01-05) must never invent `.sb` fields. The golden is its only schema authority (CLAUDE.md: "real export format, no invented fields").
Output: tools/golden/RECIPE.md, tools/golden/GoldenRuntime.cs, tools/golden/golden-1.0.7.sb (user-made, audited, approved), and live observations in the SUMMARY.
</objective>

## Planner assumptions (no CONTEXT.md: each one is flagged)

- A10 (adopted): the user-facing recipe is in Russian; code and tooling docs stay in English.
- A4 (open until the golden exists): the key names of Execute C# Method (99998) and the custom code event trigger (18002) come from this golden, not from third-party notes.
- Open Question 2 (adopted as optional): recipe step 7 extends the golden with Phase 6 example item kinds (Comment, Send Message, range If/Else, Play Sound). It is optional so Phase 1 is never blocked by it.
- The golden commit is rated `costly`, not `one-way`. A leaked value would need a local history rewrite before any push. The blocking-human decision exists for the security review RESEARCH requires, not as a reversibility gate.
- Repo hygiene: the golden is committed alone, by explicit path. Never `git add -A` or `git commit -a`. Staged deletions under `.github/ISSUE_TEMPLATE/` and untracked `.idea/` and `.claude/` stay out. The decoded review JSON goes to the session scratchpad or OS temp dir, never into the repo.
- Scope note (accepted tradeoff): the plan has 3 tasks (the `<tasks>` wrapper is not a task) and changes 3 files. It puts one implementation task (Task 1) in the same plan as two blocking checkpoints, which the sizing rules list as a split signal. This is accepted because Task 1's two files exist only to feed the user's export in Task 2, and Task 3 is the security gate on that same export. A split would add a plan boundary and one more hand-off of the review digest without adding parallelism, since both checkpoints must wait for Task 1 anyway. The implementation part is small (two files; the whole-plan estimate is 26k tokens).
